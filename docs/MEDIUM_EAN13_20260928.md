# Medium EAN-13 recovery and Retail budget

Experiment: `medium-ean13-native-20260928`. Baseline: `343cb96671f3b4b96e60ddf0527164974ca14331`.

## Scope

Improve Medium EAN-13 recovery while preserving practical Retail latency. Evaluate
both EAN13-only and Retail selection through the public JavaScript API in installed
Chrome on macOS. These are development evaluations, not an untouched holdout or a
cross-platform browser claim. The stable 1.2.2 release is separate from this preview.

## Selected algorithm

- Reuse native-length soft interpretation on unresolved 76–384-sample profiles
  with 30–85 runs and no interval ambiguity. New soft-only evidence needs
  the existing four-row consensus. Preserve the original fixed512 path.
- Extend the two existing photometric threshold hypotheses to unresolved longer
  profiles, excluding fixed512, with at most eight additional attempts per candidate.
- Reuse the existing fast source reader on at most two unresolved guard-bearing
  proposals. Require three supporting rows. Reject a new same-value read that
  intersects existing ownership; separated physical copies remain eligible.
- Reuse exact soft-profile results in two bounded slots (fixed512 and native
  length). Compare every sample bit and replay rejection traces and charged work;
  saved computation does not expand downstream budgets.
- Replace source-detail grayscale arithmetic with exactly equivalent integer
  accumulation. Its weighted sum is an integer at most 65280, followed by exact
  division by 256. Pixel values, thresholds and search coverage are unchanged.

The algorithm additions apply to Medium. The arithmetic optimization also applies
where High/Very High use source-detail sampling. No reference decoder, model,
annotation-derived crop, expected payload, new full-image pass or relaxed physical
merge rule is used.

## Quality

The full corpus has 6,980 images; 6,975 decode as image files, with 6,420 valid known
EAN-13 targets. Five corrupt files remain recorded errors. Payload matching is
one-to-one; unknown and malformed labels do not count as misses.

| Known target hits                     |           5,416 |       5,511 |         5,456 |
| Variation images, including originals |         109/345 |     115/345 |       121/345 |
| Original variation sources            |             5/5 |         5/5 |           5/5 |
| BarBeR known targets                  |     4,416/4,953 | 4,480/4,953 |   4,538/4,953 |
| Known duplicate reads, full corpus    |              48 |          52 |            12 |
| Overlapping wrong-value flags         |              10 |          10 |            14 |

The candidate gains 95 known targets without losing any baseline target. It exceeds
native Chrome in aggregate here, but still trails it on BarBeR and the small
variation set. It is not uniformly better across sources. Duplicates remain a
limitation: four more duplicate reads overall, with six newly affected cases and
offset reductions elsewhere. Do not hide these by weakening ownership checks.

One newly wrong-flagged BarBeR result matches the printed value; the frozen label
is wrong. One new unmatched output is independently confirmed from the same product
in a neighboring photograph. These are audited separately, without changing the
headline labels to improve the candidate score.

The 760-case negative/invalid-checksum/mixed-symbol control suite has no new
disallowed case/value pair: six disallowed cases remain, matching baseline.
Other-Retail evaluation gains 460→469 known targets out of 1,104, with no baseline
match lost; duplicate reads 25→26, no wrong-overlap values, and three unmatched
outputs unchanged. Ambiguous source groups are quarantined and foreign-format
labels excluded from this selected-format denominator.

Installed Chrome 153, Apple M1 Pro; full API calls on identical ImageData,
three repeats per original/variation frame and five per barcode-free frame,
rotating method order. Mean/median aggregate the per-image medians; loading is
excluded. The ordinary-photo cost is flat to slightly improved, but difficult
variations add 0.70 ms and barcode-free frames add 0.48 ms. The strict no-slowdown
goal is not fully met. This candidate is retained for review; it is not an
unqualified promotion recommendation. Common/all were not rebenchmarked here.

## Verification and retained evidence

- Core tests in all four modes: 1,222 unit tests passed.
- Public Rust tests: 1,480 passed; one explicitly ignored example test.
- Strict Clippy: core, public Rust API, C and WASM adapters in all four modes.
- 760 controls; 1,035 other-Retail frames; full native and Chrome corpus comparisons.
- Exact grayscale parity: all red/green byte combinations with representative
  blue boundary values, both RGB/RGBA layouts, every grayscale byte, plus 496
  original images with unchanged public outputs apart from elapsed time.

Experiment commands, candidate patches, hashes, failed outcomes and compact reports
are in the sibling experiment workspace under
`retained/medium-ean13-native-20260928/`. Raw image predictions and environment
identities are retained in the dataset workspace under
`datasets/metadata/medium-ean13-native-20260928/`. Original datasets remain shared;
only builds, logs and diagnostic crops are disposable.

The cheaper crop-local/source-fast variant cost about 10% Retail runtime and was
rejected. Sharpening variants produced incorrect values or lost a valid color
variation. Earlier integer-run caches did not improve Chrome speed; the selected exact
soft-profile cache reduces the barcode-free overhead. Those recipes and
counterexamples remain retained for future work; none is included here.
